# 测试用例生成

## 目标

根据用户提供的需求描述或需求文档文件，采用等价类、边界值、场景法、因果图等测试用例设计方法生成结构化的测试用例，并按规定格式写入 excel 或 xmind 文件。

## 工具清单

| 名称 | 用途 | 调用方式 | 输入 -> 输出
|---|---|---|---|
| `read_prd.py` | 从文件中读取需求描述 | `uv run scripts/read_prd.py <文件路径>` | 输入 .txt/.docx/.md/.pdf 格式文件 -> 输出带 markdown 标签的字符串 |
| `validate_cases.py` | 校验用例 json | `uv run scripts/validate_cases.py cases.json` | 输入 cases.json -> 输出校验结果：通过或失败，失败时输出错误的行和内容 |
| `export_excel.py` | 将用例写入 excel | `uv run scripts/export_excel.py cases.json` | 输入 cases.json → 输出 out.xlsx |
| `export_xmind.py` | 将用例写入 xmind | `uv run scripts/export_xmind.py cases.json` | 输入 cases.json → 输出 out.xmind |


**脚本调用规则**
- 导出为 excel 或 xmind 之前必须先调用 `validate_cases.py` 进行校验
- 脚本缺失依赖时，执行 `uv add <依赖名称>` 安装后重跑，**不修改脚本源码**
- 脚本报错时，先判断错误来源，按以下顺序处理，**先修输入，再修环境，最后才考虑改脚本**：
  1. **定位来源**（不可跳过）
     - 指向 cases.json 的字段缺失/类型错误 → 修 cases.json，**禁止改脚本**
     - ImportError / ModuleNotFoundError / 缺少依赖 → 安装依赖，**禁止改脚本**
     - 路径不存在、权限、编码 → 修调用参数或建目录，**禁止改脚本**
     - 以上均已排除，且错误明确指向脚本自身逻辑 → 进入第 2 条
  2. **受限修复**（须同时满足全部条件）
     - 能定位到具体报错行与原因
     - 改动 ≤ 10 行，仅限报错涉及的那个函数
     - 不改变输入输出契约：cases.json 结构、导出文件名、excel 列顺序、xmind 层级一律不动
     - 不升级/降级任何依赖的大版本
     - 修改前备份为 `<脚本名>.bak`
     - 修完立即重跑验证
  3. **必须停止并询问用户**
     - 需要改 cases.json 的字段定义或 schema
     - 需要改导出格式（列顺序、sheet 结构、xmind 层级）
     - 同一脚本累计自动修复 2 次仍失败 → 停止重试，向用户报告报错原文、已做改动、怀疑点
     - 需要重写整个文件、引入新依赖、或改动超过 10 行
  4. **强制汇报**：任何对脚本的修改，都必须在步骤 7 的总结中写明——改了哪个文件、第几行、改了什么、为什么必须改。不得静默修改。



## 工作流

复制下方的工作流清单，并根据它跟踪你的进度：

```
工作流清单

- [] 步骤1：获取需求
- [] 步骤2：分析需求
- [] 步骤3：设计测试用例
- [] 步骤4：写入 cases.json
- [] 步骤5：校验 cases.json
- [] 步骤6：导出用例
- [] 步骤7：总结
```

**步骤1：获取需求**

- 如果用户是直接粘贴的需求描述文本，则直接进入第二步：需求分析
- 如果用户提供的是本地需求文档的路径，则调用: `read_prd.py` 解析读取文档内容，并使用它输出的文本


**步骤2：分析需求**

- 澄清：
  - 当需求中存在歧义或矛盾点时，要向用户询问澄清，**不要自行臆测**
  - 当需求中某个功能模块或逻辑存在多个版本，要向用户询问澄清，**不要自行臆测**
  - 当需求极度不明确时（没有提及明确的功能点、功能设计等），要向用户询问澄清，**不要自行臆测**
- 分析：
  - 对需求整体进行模块化划分
  - 提取功能点/业务流程/业务约束/权限约束/状态流转/数据流转/交互操作等关键点
  - 梳理各个模块间的关联与依赖关系


**步骤3：设计测试用例**

- 根据步骤2的分析结果，适当采用等价类、边界值、场景法等测试用例设计方法设计测试用例
- 每个功能点至少要覆盖：正向输入和异常输入，其他视情况而定
- 要根据每个功能点的实际情况，适当的生成相应数量的测试用例，不要冗余、也不要太少
- 不要自行臆测，不要过度设计
- 测试用例字段、格式、类型严格遵循 `references/cases-schema.json`


**步骤4：写入 cases.json**

- 如果当前工作空间已存在 `cases.json`，先将它删除，因为它有可能是上一轮产出的或用户手动创建的
- 字段和格式严格遵循 `references/cases-schema.json`
- 不要生成多余字段
- 必须保证 id 唯一性和连续性
- 必须保证各个字段类型和约束绝对符合 schema 定义


**步骤5：校验 cases.json**

- 调用 `validate_cases.py` 校验 `cases.json`


**步骤6：导出**

- 导出为 excel：调用 `export_excel.py`，如果用户未明确指定导出格式，则默认导出为 excel
- 导出为 xmind：调用 `export_xmind.py`


**步骤7：总结**

- 汇总：
  - 告知用户最终导出的测试用例文件路径
  - 简要汇报用例总数、正向用例数、异常用例数、边界场景用例数
- 建议：
  - 列出核心模块、需求不太明确的模块、逻辑不够完善的模块
  - 列出需要用户进一步和产品、开发确认的点
  - 给出在正式测试时的着重点、注意点和边界场景


## 限制约束
- 严格按照工作流中的步骤执行
- 不支持 `.txt/.docx/.md/.pdf` 之外的格式
- 同一个脚本最多重试 3 次
- 生成的测试用例总数不能超过 100 条，超过后重新设计测试用例，务必控制总数
- 仅生成功能业务测试用例，严禁生成接口测试、自动化测试、性能测试、安全（指跨域攻击、SQL注入等，功能业务上的安全性如价格校验、权限校验、风控功能等还是需要考虑的）测试的用例


## 需求输入示例

1. **极度不明确或与产品需求和测试用例无关的场景**

**示例1**

> 用户输入：帮我查下今天的新闻
> 回复：与产品需求和测试用例完全无关，直接拒绝并结束

**示例2**

> 用户输入：帮我测试一下这个网站的登录功能
> 回复：与生成测试用例无关，直接拒绝并结束

**示例3**

> 用户输入：帮我写几条测试用例
> 回复：没有明确的主体，不知道写什么功能的测试用例，直接拒绝并结束

**示例4**

> 用户输入：帮我写个和测试用例有关的笑话
> 回复：出现测试用例关键字，但是要求主体不是写测试用例，而是写与之有关的笑话，直接拒绝并结束


2. **需求不明确，但是有给出功能点**

**示例1**

> 用户输入：给我写几条登录功能的测试用例
> 回复：虽然不明确，没有详细的登录功能需求描述，但是具备明确的功能点：登录，可以编写几条粗颗粒度的测试用例，不要自行扩充补充，给粗的就返回粗的



## 错误应对方案

| 错误/异常 | 处理方案 |
|---|---|
| 缺少 python 环境 | 结束任务并告知用户原因，禁止自动安装 python 环境|
| 脚本缺少依赖 | 安装相应的依赖并重跑 |
| 依赖版本不支持 | 先卸载已安装的版本 -> 然后安装正确的版本 -> 最后再重跑 |
| 脚本执行失败 | 分析原因并重跑，重跑超过 3 次还失败则结束任务并告知用户原因 |
| 工作流中重要文件不存在 |  结束任务并告知用户原因 |
